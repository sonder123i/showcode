## 一句话定位

**取件现场的作战面板 + 时间决策层**——不是「帮你存取件码」，是「告诉你现在该看哪个码、还剩多少时间、值不值得现在就去」。

| 锁屏直显 | ❌ **作废** | 用户指出取快递必然会解锁手机，「零操作」卖点不成立。且第三方锁屏小组件在 Android 4.2（API 17）引入后于 Android 5.0（API 21）即被移除，唯一残留路径（常驻通知 + `VISIBILITY_PUBLIC` + RemoteViews）正是 MIUI 折叠最狠的对象。此路基本无解 |
| 基于 GPS / WiFi SSID 的位置感知 | ❌ **作废** | 被更优方案绕开：**每个取件点一个独立可配置桌面组件**（菜鸟驿站/丰巢/京东各一个，并排摆在桌面）。不需定位、不耗电、无 GMS 也能跑、不受国内 ROM 后台定位限制 |
| 方向 lean | 🔄 **A → A+C 捆绑** | 去掉锁屏后，A 的路径「解锁→看组件→找码」与在位者一样长，差异化从**交互创新**降级为**信息设计创新**，单独 A 一两周内可被跟进。C 的护城河是**数据不是代码**（众包驿站营业时间库抄不走），故必须捆绑。用户已确认选 A+C |
| 「不联网」戒律 | 🔄 **可温和突破** | **下载公共数据包 ≠ 上传个人信息**。做成「内置静态数据包 + 可选静默更新公共数据 + 用户数据永不出本机」，不违背在位者的隐私叙事，反而更实用。这是它因教条而永不做、我们可以做的那一层 |
| 新的最高风险假设 | 🆕 | **用户愿意为每个取件点在桌面各让出一个组件位吗？** 最便宜的测试不需写代码：看自己桌面还剩几个 2×2 空位 |

**核实到的在位者组件硬伤**（来自 `AndroidManifest.xml` 与三个 widget XML，是 A 的可攻击点，但都容易跟进——这正是必须捆绑 C 的原因）：

- 三个 provider **全部没有 `android:configure`** → 组件不可配置，只能显示同一份全局列表，**不能按取件点分实例**
- 尺寸仅 110×110 / 180×110 / 250×110dp，`minHeight` 全是 110dp → **无竖向大组件、无全屏单码视图**
- `updatePeriodMillis="86400000"` → **24 小时才自动刷新一次**，全靠 `CUSTOM_SMS_ADDED` 广播与 MIUI 曝光刷新（20 秒）撑着，非 MIUI 机器上组件可能长时间陈旧
- MIUI 变体 `android:enabled="false"` + 独立 `:widgetProvider` 进程 → 需运行时按 ROM 动态启用（这块脏活的经验白送）

## Persona

**陈屿**，27 岁安卓开发者，重度网购，每周 5-10 个包裹。小区里同时存在菜鸟驿站、丰巢柜、京东自提点三类取件点。Kotlin/Compose 熟手，本人即项目第一用户。

- **情境**：下班顺路取件，站在驿站扫码机或丰巢柜键盘前，手上是 5-8 个来自不同平台的待取包裹，身后可能有人排队。
- **目标**：不解锁、不翻 App、不切平台，2 秒内看到「此刻这个取件点该出示的那一个码」。
- **当前 workaround**：已装 shareven/parcel 聚合短信取件码 + 桌面小组件；但仍需在列表里翻找，小组件字号不够，锁屏看不到，柜号与取件码分离。同时保留菜鸟/丰巢官方 App 用于出示动态身份码。
- **挫败感**：
  - 站在机器前要解锁、找 App、翻列表，动作链太长，后面有人催
  - 取件码用比例字体、字号小，在柜机键盘上容易看错抄错
  - 一次取多件时，分不清哪个码属于哪个驿站/柜/哪位家人
  - 柜号和货架号跟取件码不在同一视野，要来回对照两条信息
  - 已取的历史件混在待取列表里，现场要手动排除干扰
  - 不知道丰巢还剩多少免费时长、驿站几点关门，白跑一趟或被收超时费
- **「完成」长什么样**：走到驿站抬腕或亮屏，当前取件点的全部待取码立刻占满屏幕，超大等宽字体，柜号紧贴取件码，已取的自动消失，不用点任何东西。

### 次级 Persona：帮家人取件

**陈屿的妈妈**——取件码在她自己手机上，经常打电话让子女代取，或子女把码截图发给她。

**为什么纳入**：「帮家人取件」把「找不准」问题放大一个量级——手上同时有自己和家人的多套码，且需要跨设备传递。parcel 只做了「监听本机第三方 App 通知」，没做跨设备。这是 A 方向的天然延伸场景，且老年用户对「大字号单码出示」的需求远强于对「列表管理」的需求。

### 关于「身份码」的核查纠正

前期判断「身份码第三方拿不到，只能深链跳转」**是错的**。parcel 仓库存在 `util/QrCodeUtil.kt`，配合 issue #39「不能添加淘宝和拼多多身份码」与 #37「淘宝身份码搞错了怎么退出换账号」，可确认其实现为：**用户手动录入一次自己的身份码字符串 → App 本地渲染成二维码**。即淘宝/拼多多身份码是账号绑定的静态 ID，可离线重现。

⚠️ **仍待验证**：菜鸟裹裹那种会话级动态身份码是否同样可本地重现。若不可，则动态码场景仍需 `ThirdPartyEntry` 式深链兜底。

## 商业角度

- **为什么是现在**：三条同时成立。
  1. 丰巢超时收费在 2026-03 再度成为公共议题，央广网与南方都市报连续报道「未经同意入柜」「超时被迫付费」，用户对「知道自己还剩多少时间」的需求被外部事件激活。
  2. 运营商推 5G 消息/RCS，传统短信解析路径开始失效，在位者的正则架构面临被动改造窗口。
  3. Android 端侧 AI（Gemini Nano / MediaPipe LLM Inference）与锁屏/小组件能力成熟，单人开发者具备做出「模型驱动解析」的算力条件。
- **谁付费**：无人付费。作者自用 + 开源社区。
- **商业化**：不商业化。收益形态是 GitHub star、贡献者、个人技术声誉，以及作者每天省下的取件时间。
- **战略意图**：`cost-center`（自用工具开源化）

### 双目标带来的硬约束

因为目标是「既解决自己麻烦、又做开源项目给别人用」，而**在位者也是 MIT 开源免费无广告**，所以：

1. **没有商业护城河，只有产品/技术护城河**——不能用「我更便宜/我没广告」打，它已经在那个位置。
2. **迁移成本极高**——老用户已调好自定义正则、已录身份码、已加桌面小组件、已给地址打标签，这些是沉没的个人配置。「稍微好一点」必死。
3. **必须继承「不联网」隐私叙事**——在位者已完成用户教育，违背它会被视为倒退。
4. 差异化必须来自**在位者产品哲学覆盖不到的维度**，而不是功能多寡。

## 桌上的方向

### 方向 A — 现场出示层 ⭐

不做取件码档案库，做「在驿站机器前 2 秒内把正确那一个码怼到眼前」：锁屏直显、超大等宽字体、位置感知自动切到当前取件点、柜号紧贴取件码、已取自动消失、丰巢临期倒计时。

- **用户价值**：取件动作链从「解锁→找 App→翻列表→定位→对照柜号」压缩到「亮屏即见」；因为知道剩余免费时长与驿站营业时间，减少白跑一趟和被收超时费。
- **商业价值**（开源视角）：打在位者的**产品哲学盲区**而非技术盲区。parcel 要跟进必须重新定义自己的产品（从「收集全」转向「出示快」），迁移成本对它很高。完整继承「不联网」叙事，无需后端，单人可维护。
- **最高风险假设**：国内 ROM（MIUI / ColorOS / HarmonyOS）对锁屏通知与常驻通知压制极严，锁屏直显可能被折叠或杀掉，导致核心卖点落空、只能退化成「超大号桌面小组件 + 一键全屏出示模式」。**必须真机验证，不能纸上推演。**
- **技术注记**：位置感知在无 GMS 的国内机器上不能用 `GeofencingClient`，需退化为 `LocationManager` 本地计算，或用 WiFi SSID 连接状态触发（更省电，且「断开家里 WiFi = 出门」信号可靠）。
- **解决**：机会 #1 #2 #3 #4 #5 #6

### 方向 B — 端侧模型解析层（已降级为 A 的可选增强）

用本地小模型替换正则，短信与通知文本直接输出结构化 JSON，不维护规则库、不要求用户写正则。

- **用户价值**：新平台新格式自动适配，彻底消灭「识别不了」和「让用户自己写正则」两类 issue。
- **商业价值**：命中在位者 41 个 issue 中约 1/3 的痛点，需求已被验证。
- **最高风险假设**：端侧模型在「精确提取 6-8 位取件码」这类任务上是否真能碾压精调正则，存在幻觉风险；且模型体积 500MB+ 与开源社区偏好的「轻量简洁」审美冲突，可能反而劝退用户。
- **降级理由**：**护城河比 A 浅**——parcel 随时可以加一个「可选模型下载」跟进，不需要重写产品定位。
- **解决**：机会 #7 #8

### 方向 C — 主动提醒决策层（已并入 A）

丰巢 18 小时倒计时、驿站营业时间、白跑一趟预警、攒够几件一起取的批量决策建议。

- **用户价值**：从「帮我记住码」升级到「帮我决定什么时候去取」。
- **商业价值**：全竞品空白，零正面竞争。
- **最高风险假设**：价值天花板可能偏低——丰巢超时费上限仅 3 元，短信本身已是一种提醒。用户是否会为省 3 元装 App 存疑；真正值钱的是「别白跑一趟」而非「别被收 3 元」。
- **并入理由**：倒计时与营业时间天然是 A 现场层要展示的信息，不单独立项。
- **解决**：机会 #6

## 我押：方向 A

三条理由：

1. **差异化打在位者的产品哲学盲区。** 它优化「全」，A 优化「快」。8 个 issue（#24 #30 #28 #45 #21 #22 #52 #51）全指向同一个未被满足的 job，而作者用「加管理功能」回应了每一个——管理功能越多，现场找码越慢。
2. **不依赖任何不确定的技术突破。** 不需要后端、不需要模型、不需要联网，单人可完成，且完整继承「不联网」隐私叙事，直接复用在位者已教育好的用户信任。
3. **#45 与 #21 是用户在自己手动补偿排序不对。**「用户替你打补丁」是需求真实性的最强信号，比任何功能请求都可信。

## 从零写 vs fork：从零写，但把 parcel 当免费参考实现

MIT 允许 fork，但建议**读它的代码和 issue 学坑，不复用它的代码**：

1. fork 在开源世界很难获得关注度（除非显著更好，那是 MariaDB / LibreOffice 级别的事）。
2. 更关键：A 的信息架构与 parcel 根本不同（现场模式 vs 档案模式），复用它的代码会把项目拽回它的设计惯性。
3. 独立项目才能吸引 star 与贡献者。

**可以白嫖的经验清单**（都是它已经踩平的坑，能省几周）：

| 坑 | 在哪 |
| --- | --- |
| MIUI 小组件要写专用变体 | `widget/ParcelWidgetMiui.kt`、`ParcelWidgetLargeMiui.kt` |
| 通知监听会被系统杀掉，需要 Worker 健康检查 | `worker/NotificationListenerHealthWorker.kt` |
| 小米要单独引导开启「通知类短信」权限 | README 使用问题 #3（权限管理→其他权限→通知类短信→始终允许） |

| F-Droid reproducible build 会失败，上架前需处理 | issue #19 |

## 关键假设

| # | 假设 | 风险类型 | 信心 | 最便宜的测试 |
| --- | --- | --- | --- | --- |
| 1 | 「取快递时的麻烦」核心是**出示慢/找不准的交互问题**，而非信息散的聚合问题。若是后者，parcel 已解决，本项目无空间 | Value | **有证据（n=1）** | 下次取件时，从走到驿站门口到拿包裹离开，逐步记录每步耗时与卡壳点（哪怕只记一次）。该记录直接判定锁屏/字号/排序/柜号四个候选功能中哪个是真痛点 |
| 2 | 国内 ROM 允许在锁屏可靠展示自定义大字号取件码 | Feasibility | **低** | 写一个只有「常驻通知 + 锁屏 PUBLIC visibility + 超大等宽字体」的最小 Demo，在 MIUI / ColorOS / HarmonyOS 三台真机上验证是否被折叠或杀掉 |
| 3 | parcel 老用户愿意迁移，即使已调好规则、已录身份码、已加小组件 | Value | 低 | 在 parcel 的 issue 区观察 #24/#30/#28 这几类请求的点赞与追评热度；或直接提供「parcel 规则/身份码导入」降低迁移成本 |
| 4 | 无 GMS 环境下，WiFi SSID 断连可作为「出门取件」的可靠触发信号 | Usability | 中 | 自己手机上跑两周，统计误触发率（在家但 WiFi 掉线）与漏触发率（出门但用流量没连过 WiFi） |
| 5 | 菜鸟裹裹的会话级动态身份码无法本地重现，只能深链兜底 | Feasibility | 中（未核实） | 抓一次菜鸟裹裹身份码页面，隔时对比二维码是否变化 |

**动手前最想先测的**：假设 #2。原因——它是 A 的核心卖点的可行性前提，成本极低（一个周末的最小 Demo），且一旦失败整个方向要重构成「桌面小组件 + 一键全屏模式」，越早知道越好。假设 #1 虽然更根本，但它的验证可以和 #2 并行（下次取件顺手记录即可）。

## 压测结果

⚠️ **未跑完整 Phase 4 四 Check 对话**，以下为压缩版自评。Check 1（用户-方向匹配）与 Check 2（JTBD 完整性）未正式验证。可用 `/压测` 补跑。

**判断**：⚠️ **有条件成立**

**理由**：差异化清晰且有在位者真实 issue 作为证据支撑，JTBD 三段完整，用户即作者本人所以匹配度天然高。但核心卖点的技术可行性（锁屏）未验证，且关键假设证据强度仅 n=1。

**条件**：

1. 锁屏直显必须在真机（尤其 MIUI / ColorOS / HarmonyOS）上验证可行性；若被折叠或杀掉，核心卖点退化为「超大号桌面小组件 + 一键全屏出示模式」，需重新评估差异化强度。
2. 关键假设证据为 n=1，动手前需完成一次现场取件计时记录。
3. 需明确回答「parcel 老用户凭什么迁移」——已调好的自定义规则、已录的身份码、已加的小组件都是沉没配置，迁移路径（如提供 parcel 规则导入）可能需要列入 MVP 范围。
